# C++ Exception Handling ABI Deep Dive

> Exception handling is the only error propagation mechanism in C++ with "zero overhead on the normal path, high overhead on the exception path." Understanding its ABI-level implementation is a prerequisite for writing correct and efficient C++ code — you must know exactly what `noexcept` saves, what `try` blocks add, and why "zero-cost exceptions" are truly zero-cost when no exception is thrown.

---

## 1. Itanium C++ ABI Exception Handling Model

The ABI specification for C++ exception handling comes from the [Itanium C++ ABI](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html), adopted by major compilers such as GCC, Clang, and ICC (MSVC uses its own SEH model — similar principles but different implementation). Its core design goals:

1. **Zero runtime overhead**: When no exception is thrown, the normal path has no additional instructions (no checks, no setup)
2. **Table-driven**: Exception handling metadata is stored in read-only sections, not embedded in the code section
3. **Language-agnostic**: The personality routine mechanism allows C++, Java, Rust, and other languages to share the same stack unwinding infrastructure

```
┌─────────────────────────────────────────────────────────────┐
│              Itanium ABI Exception Handling Architecture      │
│                                                             │
│  ┌──────────┐    throw     ┌──────────────┐    unwind       │
│  │ User     │ ──────────→ │  __cxa_throw  │ ──────────→     │
│  │ Code     │              │  Alloc excp   │   _Unwind_*     │
│  │ throw X; │              │  object       │                 │
│  └──────────┘              └──────────────┘                 │
│       │                         │                           │
│       │ catch                   │ personality               │
│       ▼                         ▼                           │
│  ┌──────────┐              ┌──────────────┐                 │
│  │ landing  │ ◄─────────── │  .eh_frame   │                 │
│  │ pad      │   Lookup     │  .gcc_except │                 │
│  └──────────┘   LSDA       │  _table      │                 │
│       │                    └──────────────┘                 │
│       │ __cxa_begin_catch                                    │
│       │ __cxa_end_catch                                      │
│       ▼                                                      │
│  ┌──────────┐                                                │
│  │ catch    │                                                │
│  │ handler  │                                                │
│  │ logic    │                                                │
│  └──────────┘                                                │
└─────────────────────────────────────────────────────────────┘
```

### Key Runtime Functions

Exception handling involves the following C++ ABI runtime functions (defined in `libc++abi` or `libstdc++`):

| Function | Responsibility |
|----------|---------------|
| `__cxa_allocate_exception` | Allocates the exception object on the heap (includes `__cxa_exception` header) |
| `__cxa_throw` | Initializes the exception object, calls `_Unwind_RaiseException` |
| `__cxa_begin_catch` | Marks the current exception as being handled, increments the handler count |
| `__cxa_end_catch` | Decrements the handler count; if zero, destructs and frees the exception object |
| `__cxa_rethrow` | Rethrows the currently-handled exception |
| `__cxa_current_primary_exception` | Gets the `__cxa_exception*` pointer of the current exception |
| `__cxa_get_exception_ptr` | Gets the exception object pointer (used for rethrow in `catch(...)`) |

## 2. Complete Flow of Exception Throwing and Catching

### 2.1 Internal Structure of `__cxa_throw`

When the compiler encounters `throw expr;`, the generated code is roughly equivalent to:

```cpp
// Pseudocode generated by the compiler for throw 42;
void* exn_obj = __cxa_allocate_exception(sizeof(int));
new (exn_obj) int(42);                        // Construct value in exception object
__cxa_throw(exn_obj,                          // Exception object pointer
            &typeid(int),                     // type_info pointer
            (void(*)(void*))&int::~int);      // Destructor pointer (nullptr for POD)
```

What `__cxa_throw` does internally:

```
__cxa_allocate_exception(size):
  1. Allocates sizeof(__cxa_exception) + size bytes of memory
  2. Returns a pointer to the payload (skipping the header)
  3. The header structure is invisible to the user

__cxa_throw(exn_obj, tinfo, dest):
  1. Initializes __cxa_exception header fields:
     - exceptionType    = tinfo
     - exceptionDestructor = dest
     - refcount         = 1
     - handlerCount     = 0
     - propagating      = 0
  2. Calls _Unwind_RaiseException(&exception_header)
  3. If _Unwind_RaiseException returns (i.e., no catch found):
     - Calls std::terminate()
```

### 2.2 `__cxa_exception` Header Layout

Memory layout of the exception object:

```
Low Address                                                     High Address
┌────────────────────────────────┬───────────────────────────┐
│    __cxa_exception Header      │    Exception Object       │
│    (64 bytes, x86-64)          │    (User Data)            │
│                                │    sizeof(T)              │
│  ┌──────────────────────────┐  │                            │
│  │ refcount                 │  │                            │
│  │ exceptionType            │  │  ← __cxa_throw returns    │
│  │ exceptionDestructor      │  │    here (pointer visible  │
│  │ unexpectedHandler        │  │    to user code)          │
│  │ terminateHandler         │  │                            │
│  │ nextException            │  │                            │
│  │ handlerCount             │  │                            │
│  │ propagating              │  │                            │
│  │ ...                      │  │                            │
│  └──────────────────────────┘  │                            │
└────────────────────────────────┴───────────────────────────┘
                                  ↑
                     Pointer seen by user code
```

The `_Unwind_Exception` struct is embedded at the beginning of `__cxa_exception`:

```cpp
struct _Unwind_Exception {
    uint64_t exception_class;    // 4-byte identifier, e.g. "GNUC" or "CLNG"
    _Unwind_Exception_Cleanup_Fn exception_cleanup;
    _Unwind_Word private_1;      // Used internally by the unwinder
    _Unwind_Word private_2;      // Used internally by the unwinder
};

struct __cxa_exception {
    std::type_info* exceptionType;
    void (*exceptionDestructor)(void*);
    std::unexpected_handler unexpectedHandler;
    std::terminate_handler terminateHandler;
    __cxa_exception* nextException;
    int handlerCount;
    int propagating;             // Used since C++11 to mark nested exceptions
    _Unwind_Exception unwindHeader;
    // ... followed by the user exception object
};
```

### 2.3 `__cxa_begin_catch` / `__cxa_end_catch`

```
__cxa_begin_catch(unwind_header):
  1. Locates the __cxa_exception header from unwind_header
  2. handlerCount++ (allows multiple catch clauses to share the same exception)
  3. Removes the exception from the "propagating" linked list
  4. Returns the exception object pointer

__cxa_end_catch():
  1. handlerCount--
  2. If handlerCount == 0 (last catch block ends):
     - Calls exceptionDestructor to destruct the exception object
     - __cxa_free_exception frees the memory
  3. Restores the context of the previous exception (nested exception support)
```

**Nested exception handling**: Each thread maintains a stack of "currently-handling exceptions." When a new exception is thrown inside a `catch` block, the new exception is linked to the current exception's linked list. `__cxa_end_catch` checks for propagating exceptions during cleanup.

### 2.4 `rethrow` Semantics

```cpp
try {
    throw 42;
} catch (int& e) {
    throw;  // rethrow — rethrows the same exception object
}
```

`throw;` (without an expression) compiles to `__cxa_rethrow()`:

```
__cxa_rethrow():
  1. Gets the currently-handled exception from thread-local state
  2. Sets propagating = 1 (tells the unwinder not to destroy this exception)
  3. Calls _Unwind_RaiseException
  4. If not caught → std::terminate()
```

Key difference: `rethrow` does not reallocate the exception object; it propagates the same object. `handlerCount` increments, and `__cxa_end_catch` will not free it until the last catch ends.

```cpp
void process() {
    try {
        throw std::runtime_error("oops");
    } catch (std::exception& e) {
        try {
            // do some cleanup...
            throw;  // Same object, no copy
        } catch (...) {
            // handlerCount == 2
            throw;  // Continue propagating
        }
        // __cxa_end_catch is called at catch block end, but handlerCount > 0, no free
    }
    // Here __cxa_end_catch handlerCount drops to 0, freeing the exception object
}
```

## 3. Stack Unwinding Mechanism

### 3.1 Unwinding Flow

When `__cxa_throw` calls `_Unwind_RaiseException`, the unwinder begins a two-phase search:

```
_Unwind_RaiseException(exception_header):

  ═══════════════════════════════════════
  Phase 1: Search Phase
  ═══════════════════════════════════════
  Starting from the throw point, traverse each frame up the call stack:
    1. Read the FDE (Frame Description Entry) from this frame's .eh_frame
    2. If the FDE has a personality routine:
       Call personality(phase=search, actions=0)
       - personality reads the LSDA
       - Checks if the current PC is within some catch range
       - Checks if the catch type matches
       If match → return _URC_HANDLER_FOUND, end search
    3. If no match, move to the previous frame, continue searching
  If the entire stack is traversed with no match → call std::terminate()

  ═══════════════════════════════════════
  Phase 2: Cleanup Phase
  ═══════════════════════════════════════
  Again starting from the throw point, traverse upward:
    1. For each frame:
       Call personality(phase=unwind, actions=UA_CLEANUP_PHASE)
       - personality returns _URC_CONTINUE_UNWIND
       - Calls the frame's cleanup action (destruct local variables)
    2. When reaching the frame where catch was found:
       personality returns _URC_INSTALL_CONTEXT
       - Restores register context
       - Jumps to the landing pad address
       - Exception is transferred to the catch block
```

**Why two phases?** Phase 1 performs a quick scan without modifying any state (does not call destructors); if there is no matching catch in the entire stack, `terminate()` can be called directly. Phase 2 actually performs destruction and control transfer. If only one phase were used, some objects might be destructed before discovering there is no catch, leaving the program state corrupted.

### 3.2 Personality Routine

The personality routine is a callback function provided by each language (or even each function), called by the unwinder on each frame. C++ uses `__gxx_personality_v0` (GCC) or `__clang_call_terminate` (Clang internally uses `__gxx_personality_v0`).

```cpp
// Personality routine signature (simplified)
_Unwind_Reason_Code __gxx_personality_v0(
    int version,
    _Unwind_Action actions,
    uint64_t exception_class,
    _Unwind_Exception* unwind_header,
    _Unwind_Context* context    // Stack frame context provided by the unwinder
);
```

Internal work of the personality routine:

```
1. Reads the current function's LSDA (Language Specific Data Area) from context
2. Parses from the LSDA:
   - call site table: which instruction ranges can throw
   - action table: type filters corresponding to each call site
   - type table: array of type_info pointers for catches
3. Finds the corresponding call site entry based on the current PC
4. If actions contain UA_SEARCH_PHASE:
   - Traverses the action chain, calling __dynamic_cast for each type_info to check type matching
   - Match found → return _URC_HANDLER_FOUND
   - No match → return _URC_CONTINUE_UNWIND
5. If actions contain UA_CLEANUP_PHASE:
   - If the current PC's catch is the target frame → set context PC to landing pad
     → return _URC_INSTALL_CONTEXT
   - If it's a cleanup (destructor) → set cleanup action → return _URC_INSTALL_CONTEXT
   - Otherwise → return _URC_CONTINUE_UNWIND
```

### 3.3 Type Matching Mechanism

C++'s catch matching rules are implemented at the ABI level through `__dynamic_cast`:

```
Can catch (Base& e) match throw Derived()?

  type_info comparison:
  ┌────────────────────────────────────────────────────┐
│ For the catch's type_info and the exception's type_info: │
│                                                    │
│ 1. Exactly equal → direct match                    │
│ 2. catch is public base → __dynamic_cast checks   │
│    inheritance chain                               │
│ 3. catch is void* → matches all exceptions         │
│ 4. catch is ... → matches all exceptions           │
│ 5. catch is pointer type → similar but uses        │
│    pointer type matching                           │
│                                                    │
│ Note: the exception object itself is NOT polymorphic!│
│ Type matching is done entirely via type_info +     │
│ __dynamic_cast                                     │
└────────────────────────────────────────────────────┘
```

## 4. `.eh_frame` and `.gcc_except_table` Sections

### 4.1 `.eh_frame` Section

`.eh_frame` uses the **DWARF CFI (Call Frame Information)** format, describing how to unwind each stack frame. It is generated when each function is compiled and merged into the final `.eh_frame` section at link time.

```
.eh_frame section structure:
┌───────────────────────────────────────────────────────────┐
│ CIE (Common Information Entry)                            │
│   - version, augmentation, code/data alignment factor     │
│   - Return address register number                        │
│   - Initial instructions (shared register save rule       │
│     baseline for all FDEs)                                │
├───────────────────────────────────────────────────────────┤
│ FDE (Frame Description Entry) — one per function          │
│   - CIE pointer                                           │
│   - Function start address (PC_begin)                     │
│   - Function length (PC_range)                            │
│   - CFI instruction sequence for this function            │
│     Describes: where each register is saved at each       │
│                instruction position                       │
│                how to compute the CFA                      │
│                (Canonical Frame Address)                   │
│   - LSDA pointer (if exception handling is present)       │
├───────────────────────────────────────────────────────────┤
│ FDE — another function                                    │
│   ...                                                     │
├───────────────────────────────────────────────────────────┤
│ .eh_frame_hdr (optional, accelerates lookup)              │
│   - Binary search table: PC → FDE mapping                 │
└───────────────────────────────────────────────────────────┘
```

CFI instruction example:

```
# CFI annotations for function prologue (auto-generated by compiler)
.cfi_startproc                    # FDE begins
.cfi_def_cfa_offset 16            # CFA = RSP + 16
.cfi_offset 6, -16                # RBP saved at [CFA-16]
pushq %rbp                        # push rbp
.cfi_def_cfa_offset 24            # CFA = RSP + 24
.cfi_offset 6, -24                # RBP save location updated
movq %rsp, %rbp
.cfi_def_cfa_register 6           # CFA = RBP
...
.cfi_endproc                      # FDE ends
```

The unwinder uses this information to, at any instruction position:
1. Compute the CFA (caller's stack pointer)
2. Find the restore location for each saved register
3. Restore the caller's register set

### 4.2 `.gcc_except_table` (LSDA Section)

`.gcc_except_table` contains the **LSDA (Language Specific Data Area)** for each function that needs exception handling. The personality routine reads the LSDA to decide how to handle exceptions in the current frame.

```
.gcc_except_table structure:
┌───────────────────────────────────────────────────────────┐
│ LSDA Header                                               │
│   - LPStart: landing pad base address (usually the        │
│     function start address)                               │
│   - TTBase: type table base offset                        │
│   - Call site table encoding                              │
│   - Call site table length                                │
├───────────────────────────────────────────────────────────┤
│ Call Site Table                                           │
│   Each entry describes a potentially-throwing code range:  │
│   ┌──────────┬──────────┬──────────┬──────────┐           │
│   │ CS_start │ CS_len   │ CS_lp    │ CS_action│           │
│   │ Start    │ Length   │ LP       │ Action   │           │
│   │ offset   │          │ offset   │ index    │           │
│   │          │          │ (0=none) │          │           │
│   └──────────┴──────────┴──────────┴──────────┘           │
├───────────────────────────────────────────────────────────┤
│ Action Table                                              │
│   Linked list structure, each entry:                      │
│   ┌──────────┬──────────┬──────────┐                      │
│   │ AR_filter │ AR_disp  │ AR_next  │                      │
│   │ Type table│ Next     │ List     │                      │
│   │ index     │ action   │ pointer  │                      │
│   │ (0=cleanup│ offset  │ (0=end)  │                      │
│   └──────────┴──────────┴──────────┘                      │
├───────────────────────────────────────────────────────────┤
│ Type Table                                                │
│   type_info* array (reverse order, index 1 = first catch   │
│   type)                                                   │
│   [0] = nullptr (reserved)                                │
│   [1] = &typeid(int)                                      │
│   [2] = &typeid(std::exception)                           │
│   ...                                                     │
└───────────────────────────────────────────────────────────┘
```

### 4.3 A Complete Example

```cpp
void foo() {
    Widget w;              // Needs destruction
    try {
        bar();             // May throw
        baz();             // May throw
    } catch (int e) {
        handle_int(e);
    } catch (const std::exception& e) {
        handle_exn(e);
    }
    // w's destructor runs at function end
}
```

Generated LSDA (conceptual representation):

```
Call Site Table:
  ┌────────────┬────────────┬────────────┬───────────┐
  │ CS_start   │ CS_len     │ CS_lp      │ CS_action │
  ├────────────┼────────────┼────────────┼───────────┤
  │ bar call   │ bar call   │ LP1        │ 1         │
  │ location   │ length     │            │           │
  │ baz call   │ baz call   │ LP1        │ 1         │
  │ location   │ length     │            │           │
  └────────────┴────────────┴────────────┴───────────┘
  LP1 points to catch entry

Action Table:
  Action 1: AR_filter=1, AR_disp=sizeof(Action), AR_next=2
  Action 2: AR_filter=2, AR_disp=0,            AR_next=0

Type Table:
  [1] = &typeid(int)
  [2] = &typeid(std::exception)

Matching logic (personality routine):
  1. Exception type = typeid(Widget) or other
  2. First check Action 1 (int) → no match
  3. Follow linked list to Action 2 (std::exception) → check __dynamic_cast
  4. If neither matches → propagate to the previous frame
```

## 5. Zero-Cost Exception Model (Table-Driven)

### 5.1 Why It's Called "Zero-Cost"

"Zero-cost" refers to **zero runtime cost when no exception is thrown** — it does not mean throwing is free; quite the opposite:

```
Comparing two exception implementation models:

┌──────────────────────────────────────────────────────────────┐
│ Model 1: DWARF Unwinding (Itanium ABI / GCC / Clang default) │
│                                                              │
│ Normal path: zero instruction overhead                       │
│   - No setjmp, no state checks                               │
│   - Unwinding info is entirely in .eh_frame /                │
│     .gcc_except_table sections                               │
│   - These tables are only read when a throw occurs           │
│                                                              │
│ Exception path: high cost                                    │
│   - Two-phase stack unwinding (traverses entire call         │
│     stack twice)                                             │
│   - Personality routine called per frame                     │
│   - type_info comparison (may involve string comparison      │
│     or dynamic_cast)                                         │
│   - Table lookup overhead (linear or binary search)          │
│                                                              │
│ Trade-off: increased code size (exception tables + landing   │
│ pads), ICache pressure                                       │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ Model 2: SJLJ (SetJump/LongJump, some embedded/legacy        │
│ systems)                                                     │
│                                                              │
│ Normal path: each try block + setjmp (~10-20 instructions)   │
│   - setjmp called on every entry to a try block to save      │
│     registers                                                │
│   - Space: ~200 bytes jmp_buf per try block                  │
│                                                              │
│ Exception path: relatively fast                              │
│   - longjmp jumps to setjmp point, only one step             │
│   - But must manually call destructors along the way         │
│     (if any)                                                 │
│                                                              │
│ Trade-off: normal path is slow ~10-20 instructions/try block │
└──────────────────────────────────────────────────────────────┘
```

**Which to choose?** Nearly all modern compilers use the table-driven (DWARF) model, because "not throwing" is the norm for the vast majority of code. SJLJ is only used when the target platform does not support DWARF unwinding (e.g., some embedded ARM, iOS 32-bit).

GCC can be explicitly selected:
```bash
gcc -fexceptions -fsjlj-exceptions    # Force SJLJ
gcc -fexceptions -fnon-call-exceptions # Allow exceptions at non-call sites (e.g., signals)
```

### 5.2 Code Size Cost

Zero-cost exceptions are not free — they trade disk space for zero runtime overhead:

```
Every try-catch block and every potentially-throwing function call in source code produces:

1. FDE entries in .eh_frame
   - Typically 32-128 bytes per function
   - Even without exception handling, needed for debugger backtraces

2. LSDA in .gcc_except_table
   - Call site table: ~8-16 bytes per potentially-throwing call site
   - Action table: ~8 bytes per catch type
   - Type table: ~8 bytes per catch type_info*

3. Landing pads in the code section
   - Catch block code (may be placed in cold paths)
   - Cleanup code (destructor calls)

Actual data (typical C++ program):
  .eh_frame         ~5-15% of binary size
  .gcc_except_table ~1-5% of binary size
  landing pads      ~1-3% of code section
```

## 6. How `noexcept` Works

### 6.1 How Compilers Handle `noexcept`

The ABI-level effect of `noexcept` is **not generating landing pads and corresponding LSDA entries for that function**:

```cpp
void safe() noexcept {
    // Compiler knows this function promises not to throw
    // No exception table entries generated
}

void unsafe() {
    // Compiler generates call site table entries for every
    // potentially-throwing call site
    // Generates landing pads for catch blocks
}
```

Code generated by the compiler for `noexcept` functions:

```
safe() noexcept:
  ; Normal code...
  ; If there's an internal throw → compiler directly generates __cxa_call_terminate
  ; instead of going through the stack unwinding mechanism
  ; No LSDA needed in .gcc_except_table

unsafe():
  ; Normal code...
  ; Each potentially-throwing call site has a .gcc_except_table entry
  ; If there's try-catch, there's a corresponding landing pad
```

**What does `noexcept` save?**
1. No call site entries generated in `.gcc_except_table` (reduces table size)
2. Allows more aggressive code motion (compiler knows it won't be interrupted by exceptions)
3. Reduces landing pad code (cold paths don't bloat)

### 6.2 `noexcept` and `__cxa_call_terminate`

When a `noexcept` function actually throws an exception:

```cpp
void f() noexcept {
    throw 42;  // UB! But the compiler inserts a fallback
}
```

The compiler inserts checks at **every potentially-throwing call site** in a `noexcept` function:

```
# Generated code for f() (simplified)
f:
    call some_throwing_function
    # If some_throwing_function returns normally, continue
    ret

# However! The compiler also marks this function as noexcept in the unwind tables
# When the unwinder encounters a noexcept frame during Phase 2:
#   personality routine returns _URC_FATAL_PHASE1_ERROR
#   → __cxa_call_terminate() → std::terminate()
```

In practice, GCC/Clang do not insert explicit checks at every call site. Instead, they rely on the unwinder's handling when it discovers a noexcept frame during unwinding: the personality routine sees that the function is marked as noexcept in the LSDA, directly returns an error code, and the unwinder calls `std::terminate()`.

### 6.3 Conditional `noexcept`

```cpp
void maybe_throw() noexcept(sizeof(T) <= 64) {
    // If T satisfies the condition → noexcept
    // Otherwise → allows exception propagation
    // Compiler chooses one mode for the entire function
}
```

Conditional `noexcept` is evaluated at compile time; when the result is `true`, it is equivalent to `noexcept`; when `false`, it is equivalent to no exception specification. The standard library uses it extensively:

```cpp
// std::vector's move constructor
vector(vector&& other) noexcept;  // Move semantics guarantee no throw

// std::swap default implementation
template <typename T>
void swap(T& a, T& b) noexcept(noexcept(T(std::move(a))) &&
                                 noexcept(a.operator=(std::move(b))));
```

## 7. Exception Object Memory Management

### 7.1 Allocation Strategy

```
__cxa_allocate_exception(size):
  ┌──────────────────────────────────────────────────┐
  │ Default strategy: malloc(size + sizeof(__cxa_exception)) │
  │                                                  │
  │ This means throw std::string("hello") requires:  │
  │   sizeof(__cxa_exception) ≈ 120 bytes (x86-64)   │
  │ + sizeof(std::string) ≈ 32 bytes                 │
  │ + heap string data (if exceeding SSO threshold)   │
  │                                                  │
  │ Total: ~152+ bytes heap allocation                │
  │                                                  │
  │ ⚠️ If malloc fails → std::terminate()            │
  │ (Cannot use exceptions to handle exception        │
  │ allocation failure — logically unsolvable)        │
  └──────────────────────────────────────────────────┘
```

### 7.2 Exception Object Reference Counting

The `refcount` field in the `__cxa_exception` header manages sharing:

```
Scenario 1: Normal catch — refcount = 1
  throw → catch → end_catch → refcount=0 → free

Scenario 2: Rethrow — refcount increases
  throw(1) → catch → rethrow(2) → catch → end_catch(2→1)
                                   → end_catch(1→0) → free

Scenario 3: std::exception_ptr — refcount increases
  throw(1) → catch → current_exception(refcount++) → end_catch(1→1)
  // exception_ptr holds a reference, exception object not freed
  // When exception_ptr is destructed, refcount-- → 0 → free
```

```cpp
std::exception_ptr ep;
try {
    throw std::runtime_error("oops");
} catch (...) {
    ep = std::current_exception();  // refcount++
}  // end_catch: refcount 1→1 (not freed)
// When ep is destructed: refcount 1→0 → exception object freed
```

## 8. Exception Specifications

### 8.1 Dynamic Exception Specifications (Removed since C++17)

```cpp
// C++98/03 exception specifications — deprecated and removed
void f() throw(int, std::exception);  // Only allows throwing int or std::exception
void g() throw();                      // Does not allow throwing anything (equivalent to noexcept)

// Since C++17: throw() is equivalent to noexcept
// throw(Type...) has been completely removed
```

Dynamic exception specifications were implemented by the compiler inserting type checks at every throw site; if the thrown type was not in the allowed list, `std::unexpected()` was called. This incurred runtime overhead and had confusing semantics when interacting with templates.

### 8.2 `noexcept` Replaces Dynamic Exception Specifications

```
Dynamic exception specs (deprecated):   noexcept (modern):
  - Runtime checks                      - Compile-time constraint
  - Overhead at every throw site        - No exception table entries generated
  - Violation calls unexpected()        - Violation calls terminate()
  - Difficult interaction with templates - Conditional noexcept works perfectly
                                           with templates
  - Removed from C++17 standard         - The only exception specification
                                           mechanism
```

## 9. Impact of `-fno-exceptions`

### 9.1 Compiler Behavior When Exceptions Are Disabled

```bash
g++ -fno-exceptions program.cpp
```

```
Effects of -fno-exceptions:

┌────────────────────────────────────────────────────────────┐
│ 1. throw statements → compile error (not a runtime         │
│    behavior change)                                        │
│    error: exception handling disabled, use '-fexceptions'  │
│                                                            │
│ 2. try / catch → compile error                             │
│                                                            │
│ 3. Standard library code that uses exceptions:             │
│    - No exception tables generated                         │
│    - __cxa_throw is not called                             │
│    - __throw_* functions become no-ops or directly call    │
│      std::abort                                            │
│                                                            │
│ 4. .eh_frame section is still generated (debugger needs    │
│    backtrace information)                                  │
│    But .gcc_except_table is basically empty                │
│                                                            │
│ 5. Landing pad code not generated → code section shrinks   │
└────────────────────────────────────────────────────────────┘
```

### 9.2 `-fno-exceptions` and Standard Library Compatibility Issues

```cpp
std::vector<int> v;
v.at(5);  // at() throws std::out_of_range
          // Under -fno-exceptions: calls std::abort()
          // Instead of throwing — your program crashes immediately
```

Standard library functions that are not `noexcept` (such as `std::vector::at`, `std::stoi`, container `push_back`, etc.) have **behavior not defined by the standard** under `-fno-exceptions` — it is effectively implementation-defined. GCC's libstdc++ replaces `__throw_*` functions with `std::abort()` in this mode.

### 9.3 When to Use `-fno-exceptions`

```
Suitable for:
  - Embedded systems (no heap space to allocate exception objects)
  - Real-time systems (exception unwinding latency is unpredictable)
  - GPU code (exceptions not supported)
  - C interface layers (C does not understand exceptions)

Not suitable for:
  - General-purpose code using the standard library
  - Code that relies on RAII (destructors depend on stack unwinding)
  - Library code (cannot require users to also disable exceptions)
```

**Modern alternative**: Use `noexcept` to annotate non-throwing functions, use `std::expected` (C++23) or `std::variant` for error propagation, rather than globally disabling exceptions.

## 10. Exception Safety Guarantees

### 10.1 Three Guarantee Levels

```
┌─────────────────────────────────────────────────────────────┐
│ Nothrow Guarantee                                           │
│                                                             │
│ The operation promises not to throw any exception.           │
│ All destructors, move operations, and swap must satisfy     │
│ this guarantee.                                             │
│                                                             │
│ void swap(T& a, T& b) noexcept;  // Required               │
│ ~T() noexcept;                    // Implicitly noexcept    │
│                                    since C++11              │
│ T(T&&) noexcept;                  // Move construction      │
│ T& operator=(T&&) noexcept;       // Move assignment        │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ Strong Guarantee                                            │
│                                                             │
│ If the operation throws an exception, program state rolls   │
│ back to before the operation began.                         │
│ Either the operation fully succeeds, or state is unchanged. │
│                                                             │
│ std::vector::push_back strategy:                            │
│   1. If expansion needed: allocate new memory first (may    │
│      throw)                                                 │
│   2. Copy/move elements to new memory (may throw)           │
│   3. Free old memory                                        │
│   If step 1 or 2 throws → vector remains unchanged         │
│   (strong)                                                  │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ Basic Guarantee                                             │
│                                                             │
│ If the operation throws an exception:                       │
│   - No resource leaks (RAII guarantee)                      │
│   - All objects are still in a valid state (but not         │
│     necessarily which state)                                │
│   - Can be safely destroyed or reassigned                   │
│                                                             │
│ std::vector::operator= copy-and-swap implementation:        │
│   Widget& operator=(Widget other) {  // By value, may throw │
│       swap(*this, other);            // noexcept            │
│       return *this;                  // other destructed,   │
│   }                                  // safe                │
│   If constructing other throws → this unchanged (strong)    │
│   If implementation is not copy-and-swap → may only be      │
│   basic                                                     │
└─────────────────────────────────────────────────────────────┘
```

### 10.2 Key Patterns for Writing Exception-Safe Code

```cpp
// Pattern 1: Prepare first, then commit (strong guarantee)
void ResourceManager::addResource(Resource r) {
    // Step 1: Prepare new state (may throw)
    auto new_vec = resources_;        // Copy (may throw)
    new_vec.push_back(std::move(r));  // May throw (if expansion needed and move throws)

    // Step 2: Commit (noexcept)
    resources_ = std::move(new_vec);  // Move assignment noexcept
}

// Pattern 2: RAII + explicit noexcept annotations
class Database {
    Connection conn_;
    std::mutex mtx_;
public:
    // Destructor, move, swap are all noexcept
    ~Database() noexcept { conn_.close(); }
    Database(Database&& o) noexcept : conn_(std::move(o.conn_)) {}
    void swap(Database& o) noexcept {
        using std::swap;
        swap(conn_, o.conn_);
    }
};
```

## 11. Performance Cost Analysis

### 11.1 Normal Path Cost

```
Normal path cost of table-driven exceptions:

┌────────────────────────────────────────────────────────────┐
│ Direct runtime cost: zero                                   │
│   - No check for "are we in a try block"                    │
│   - No setjmp/longjmp calls                                 │
│   - No exception state linked list maintained               │
│                                                            │
│ Indirect costs (very significant):                          │
│                                                            │
│ 1. Code size bloat (ICache pressure)                        │
│    - Landing pad code: ~1-5% of code section                │
│    - But this code is on cold paths, usually in separate    │
│      .text sections                                         │
│    - Compiler places catch code at function end or in       │
│      separate sections                                      │
│                                                            │
│    GCC: -ffunction-sections + -fdata-sections               │
│    Linker: --gc-sections can remove unused landing pads     │
│                                                            │
│ 2. .eh_frame section size                                   │
│    - Every function has an FDE entry (for debugger          │
│      backtraces)                                            │
│    - Typically 5-15% of binary size                         │
│    - Can be reduced with -fno-asynchronous-unwind-tables    │
│      (but breaks backtraces and debugging)                  │
│                                                            │
│ 3. Increased compile time                                   │
│    - Generating exception tables requires analyzing each    │
│      function's control flow                                │
│    - Determining which call sites may throw                 │
│    - Generating control flow graphs for landing pads        │
│                                                            │
│ 4. Increased link time                                      │
│    - Merging multiple .eh_frame sections                    │
│    - Generating .eh_frame_hdr (binary search table)         │
└────────────────────────────────────────────────────────────┘
```

### 11.2 Exception Path Cost

```
Cost of throwing an exception:

__cxa_allocate_exception:  ~1 malloc (100-200 bytes)
_Unwind_RaiseException:
  Phase 1 (search):
    - Traverse each frame: read .eh_frame → parse FDE → call personality
    - ~1-5 μs per frame (depending on LSDA complexity)
    - With call stack depth N, approximately N × 2-5 μs
  Phase 2 (cleanup):
    - Traverse again, cleaning up frame by frame
    - Call each local object's destructor
    - ~2-10 μs per frame (plus destructor execution time)
  Total: ~O(N) stack depth × per-frame unwinding overhead

Measured data (x86-64, GCC 13, -O2):
  Call stack depth 10:  ~5-20 μs
  Call stack depth 50:  ~25-100 μs
  Call stack depth 200: ~100-400 μs
  (excluding destructor execution time)

Comparison: normal function return ~1 ns
  Exceptions are 1000-100000× slower than normal returns
  Therefore: exceptions should only be used for truly exceptional situations
```

### 11.3 Comparison with Error Codes

```
                  Exception       Return               Return
                                  std::expected        error code
Normal path       Indirect        ~0-1 instructions    ~0-1 instructions
                  ICache          (check optional)     (if check)
                  overhead
Error path        ~10-400 μs     ~10-50 ns            ~1-5 ns
                  (stack         (construct expected)  (return int)
                  unwinding)
Code              None            Check at each        Check at each
intrusiveness     (automatic      return point         return point
                  propagation)
Type safety       Strong          Strong               Weak (int error
                                                        code)
Composability     Automatic       Needs ? or           Manual
                  propagation     and_then chaining    propagation
                  (multi-layer
                  call chains)
```

## 12. `setjmp/longjmp` Alternatives and Their Pitfalls

### 12.1 SJLJ Exception Model

In C, `setjmp/longjmp` is sometimes used to simulate exceptions:

```cpp
#include <csetjmp>

static std::jmp_buf jump_buffer;
static volatile bool exception_thrown = false;

void throw_logic_error(const char* msg) {
    exception_thrown = true;
    std::longjmp(jump_buffer, 1);
}

void risky_operation() {
    // ... may go wrong
    if (error) throw_logic_error("something went wrong");
}

int main() {
    if (setjmp(jump_buffer) == 0) {
        // Normal path
        risky_operation();
    } else {
        // Exception path
        std::cout << "Caught error\n";
    }
}
```

### 12.2 Why SJLJ Is Worse Than C++ Exceptions

```
┌──────────────────────────────────────────────────────────────┐
│ SJLJ vs C++ Exceptions: point-by-point comparison            │
│                                                              │
│ 1. Normal path overhead                                      │
│    SJLJ:  setjmp at each try point ~10-20 instructions +     │
│           register save                                      │
│    C++:   zero instructions                                  │
│                                                              │
│ 2. Destructor calls                                          │
│    SJLJ:  longjmp skips intermediate frames → destructors    │
│           NOT called → resource leaks!                       │
│    C++:   automatic stack unwinding → destructors called     │
│           frame by frame                                     │
│    ⚠️ This is SJLJ's most fatal problem                      │
│                                                              │
│ 3. Type safety                                               │
│    SJLJ:  no type information, can only use error codes      │
│    C++:   full type information + catch matching             │
│                                                              │
│ 4. Cross-language propagation                                │
│    SJLJ:  cannot cross function boundaries (setjmp and       │
│           longjmp must be in the same scope)                 │
│    C++:   can cross any number of function call layers       │
│                                                              │
│ 5. Nesting support                                           │
│    SJLJ:  must manually manage jmp_buf stack                 │
│    C++:   automatic nested exception support                 │
│                                                              │
│ 6. Exception safety                                          │
│    SJLJ:  objects are in indeterminate state after longjmp   │
│    C++:   all local objects are properly destructed           │
│                                                              │
│ 7. Compiler optimization                                     │
│    SJLJ:  setjmp is an opaque call → hinders optimization    │
│    C++:   exception path is cold code → doesn't affect       │
│           normal path optimization                           │
└──────────────────────────────────────────────────────────────┘
```

The devastating consequences of `longjmp`:

```cpp
void dangerous() {
    std::string name = "hello";   // Constructor allocates heap memory
    std::mutex mtx;                // Constructor initializes mutex
    mtx.lock();                    // Acquires lock
    if (error) longjmp(buf, 1);   // Jump!
    mtx.unlock();
    // Neither name's nor mtx's destructor will be called
    // → Memory leak
    // → Mutex is never released (deadlock)
}
```

### 13.2 Analyzing a Function's Exception Table

Source code:

```cpp
// example.cpp
#include <stdexcept>

int compute(int x) {
    if (x < 0) throw std::invalid_argument("negative");
    return x * 2;
}

int process(int x) {
    int result = 0;
    try {
        result = compute(x);
    } catch (const std::exception& e) {
        result = -1;
    }
    return result;
}
```

Compile and analyze:

```bash
g++ -O2 -S example.cpp -o example.s
```

Key generated assembly (x86-64 simplified):

```asm
process(int):
    # Function entry
    .cfi_startproc
    .cfi_personality 155, __gxx_personality_v0  # personality routine
    .cfi_lsda 0x1b, .Lexception0               # LSDA pointer

    # Normal code
    pushq   %rbx
    .cfi_def_cfa_offset 16
    .cfi_offset 3, -16
    movl    %edi, %ebx
    call    compute(int)         # ← call site entry 1

    # Normal return path
    movl    %ebx, %eax
    popq    %rbx
    ret

    # Landing pad (cold path, compiler places at end of function)
    .Lexception0:
    cmpq    $1, %rdx             # Check exception type
    je      .Lcatch_handler
    .cfi_def_cfa_offset 16
    call    _Unwind_Resume       # Non-matching type, continue unwinding

    .Lcatch_handler:
    # __cxa_begin_catch
    movq    %rax, %rdi
    call    __cxa_begin_catch
    # Catch block body
    movl    $-1, %ebx            # result = -1
    # __cxa_end_catch
    call    __cxa_end_catch
    jmp     .Lreturn             # Jump back to normal path
    .cfi_endproc
```

Corresponding `.gcc_except_table` (conceptual representation):

```
LSDA for process:
  LPStart:        process function start address
  TTBase:         type table offset
  Call Site Table:
    CS_start: compute(int) call location
    CS_len:   5 (call instruction length)
    CS_lp:    .Lexception0 offset
    CS_action: 1 (→ Action Table index 1)
  Action Table:
    Action 1: filter=1 → type table [1]
              next=0
  Type Table:
    [1] = &typeid(std::exception)   # catch(const std::exception&)
```

```cpp
int unsafe_compute(int x) {
```


### 13.4 Reading `.eh_frame` with `readelf`

```bash
$ readelf --debug-dump=frames example.o

Contents of the .eh_frame section:

00000018 0000001c 0000001c FDE cie=00000000 pc=00000000..0000002a
   LOC           CFA      rbx   rbp   ra
0000000000000000 rsp+8    u     u     c-8
0000000000000002 rsp+16   c-8   u     c-8
0000000000000005 rsp+24   c-8   c-16  c-8
```

Interpretation:
- `CFA = rsp+8`: At function entry, CFA (caller stack pointer) = RSP + 8 (skipping return address)
- `c-8`: That register is saved at [CFA - 8]
- Each row corresponds to a register save rule change at an instruction address

## 14. Differences Between MSVC SEH and Itanium ABI

MSVC uses Windows SEH (Structured Exception Handling) to implement C++ exceptions:

```
┌──────────────────────────────────────────────────────────────┐
│                 Itanium ABI          MSVC (x64)               │
│ Exception model   table-driven       table-driven (x64)       │
│                              or      frame-based (x86/32)     │
│ Metadata          .eh_frame          .pdata + .xdata          │
│ storage           .gcc_except_table  (shared with SEH)        │
│ Unwind info       DWARF CFI          RUNTIME_FUNCTION         │
│ format                                                         │
│ Personality       __gxx_personality  __CxxFrameHandler3/4     │
│ Exception object  Heap-allocated     Stack unwinding +        │
│                   (__cxa_*)          compiler-managed          │
│ SEH hardware      N/A                Windows kernel-level     │
│ support                                support (Vectored      │
│                                        Exception)             │
│ Type matching     __dynamic_cast     Compiler-generated       │
│                                        catch info             │
│ Exception chain   __cxa_exception    ExceptionRegistration    │
└──────────────────────────────────────────────────────────────┘
```

Key difference: MSVC on x64 uses `__CxxFrameHandler3` as the personality routine, with exception tables stored in the PE file's `.pdata` and `.xdata` sections rather than ELF's `.eh_frame`. On x86 (32-bit), MSVC uses frame-based SEH (placing `EXCEPTION_REGISTRATION` structures on the stack), which adds overhead to the normal path.

## 15. Common Pitfalls and Best Practices

### 15.1 Exceptions in Destructors

```cpp
// ❌ Fatal: destructor throws an exception
struct Bad {
    ~Bad() {
        close(fd);  // If close fails and throws
        // → throwing during stack unwinding → std::terminate()
    }
};

// ✅ Correct: destructor swallows exceptions
struct Good {
    ~Good() noexcept {
        try { close(fd); }
        catch (...) { /* Log, do not propagate */ }
    }
};
// Since C++11, destructors are implicitly noexcept — no need for explicit annotation
```

### 15.2 Exceptions and `std::move`

```cpp
// ❌ Dangerous: exception thrown after move operation completes
void process(Widget w) {
    Widget other = std::move(w);  // Move
    risky_call();                  // If this throws
    // w has been moved-from, is in a valid but unspecified state
    // If process is part of a copy assignment operator
    // → may violate basic guarantee
}

// ✅ Do all potentially-throwing work first, then noexcept commit
void safe_process(Widget w) {
    risky_call();                  // May throw, but w hasn't been moved yet
    Widget other = std::move(w);  // noexcept
}
```

### 15.3 Correct Use of `catch(...)`

```cpp
void worker() {
    try {
        do_work();
    } catch (...) {
        // Log exception info
        log_exception();
        // Option 1: Rethrow
        throw;
        // Option 2: Convert to error code
        // return ErrorCode::UNKNOWN;
        // Option 3: Use exception_ptr to pass to another thread
        // ep = std::current_exception();
    }
}
```
