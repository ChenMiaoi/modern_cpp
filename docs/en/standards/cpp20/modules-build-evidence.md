# Modules Build Practice (BMI, Dependency Scanning, CMake Integration, and Compiler Differences)

## Overview

Correct use of Modules is not just a language-level problem but a build-system-level problem. From `import` statements to final linking, the process involves BMI (Binary Module Interface) file generation and consumption, dependency scanner topological sorting, CMake/Ninja module-aware scheduling, and format differences between compilers. This article provides a complete build walkthrough from principles to runnable examples, covering BMI format details, minimal CMake projects, the differences between Header Units and Named Modules, Global/Private Module Fragment, template instantiation behavior, ABI vs BMI stability, practical differences across the three major compilers, Partition organization patterns, and migration strategies.

## BMI (Binary Module Interface) File Format

### What is BMI

BMI is the **intermediate artifact** generated by the compiler when compiling a module interface unit, containing all exported declarations, type information, and the compiled representation of inline definitions. Consumers (translation units that `import` the module) read the BMI rather than source code.

```
Build flow:

math.cppm → [Compiler] → math.gcm / math.ifc / module.pcm
               ↓                      ↓
           math.o (implementation)  BMI cache file
                                     ↓
main.cpp → [import math] → read BMI → main.o
                                              ↓
                              link → math.o + main.o → a.out
```

### Format Details (Compiler-Specific)

BMI format is **not specified by the standard**; each compiler has its own implementation and they are **not cross-version compatible**.

**MSVC (.ifc)**:
```
IFC (Interface Container) format:
- Binary serialization format, containing:
  - Module name and partition information
  - AST nodes of exported declarations
  - Type information (classes, enums, typedef)
  - Inline function bodies and template definitions
  - References to other module dependencies
- MSVC IFC format documentation: partially public, in the ifc-spec project
- File size: typically 10KB-10MB depending on module complexity
```

**Clang (.pcm)**:
```
PCM (Precompiled Module) format:
- Based on LLVM bitcode format
- Contains serialized AST and type tables
- Stored in the directory specified by -fprebuilt-module-path
- Uses .pcm extension, but internal format is LLVM bitcode
- Clang module cache path: -fmodules-cache-path=<dir>
```

**GCC (.gcm)**:
```
GCM (GCC Compiled Module) format:
- GCC proprietary binary format
- Stored using reversed module name path:
  C++ → c++/C.gcm
  math_utils → math_utils.gcm
- Default storage in the -fmodules-ts output directory
- GCC 14+ basic functionality available, but stability issues remain
```

### BMI Non-Portability

```
Cross-compiler compatibility:

MSVC .ifc  ←✗→  Clang .pcm   ←✗→  GCC .gcm
  ↑                 ↑                 ↑
  MSVC only         Clang only        GCC only

Even different versions of the same compiler are incompatible:
MSVC 19.38 .ifc  ←✗→  MSVC 19.39 .ifc
```

**Practical constraint**: All developers must use the same compiler at the same version. CI/CD must lock the compiler version.

## Dependency Scanning: CMake/Ninja Module Dependency Scanning

### Why Dependency Scanning is Needed

Traditional header file dependencies are visible through `#include` (text substitution). Module `import` dependencies can only be determined **after parsing source code** — the compiler must know which source file `math` corresponds to in `import math;`.

```
Traditional build: dependencies visible in source code
main.cpp
  ├── #include "math.h"     ← preprocessor directly sees
  ├── #include "utils.h"
  └── ...

Modules build: dependencies require scanning
main.cpp
  ├── import math;           ← need to know where math is
  ├── import std;            ← need to know where std is
  └── ...
```

### P1689R5: Standard Dependency Format

P1689R5 defines a standard JSON format for module dependency information:

```json
{
  "rules": [
    {
      "primary-output": "math.pcm",
      "provides": [
        { "logical-name": "math", "is-interface": true }
      ],
      "requires": [
        { "logical-name": "std" }
      ]
    },
    {
      "primary-output": "main.o",
      "requires": [
        { "logical-name": "math" },
        { "logical-name": "std" }
      ]
    }
  ]
}
```

### Scanning Flow

```
CMake module build flow (3 phases):

Phase 1: Dependency scanning (P1689 scanner)
  ├── Scan all .cppm / .cpp files
  ├── Extract import and export module declarations
  ├── Generate dependency graph (JSON)
  └── Output topological sort results

Phase 2: Topologically sorted compilation
  ├── Compile dependency-free module interfaces first
  ├── Then compile interfaces that depend on already-compiled modules
  ├── Then compile implementation units and ordinary source files
  └── Compilation order guarantee: depended-on before dependent

Phase 3: Linking
  └── All .o files linked into final target
```

## Header Unit vs Named Module

```cpp
// Header Unit: import traditional header files as modules
import <vector>;       // Header Unit
import <iostream>;

// Named Module: the standard's new module form
import std;            // Named Module (C++23 import std)
import math_utils;     // user-defined Named Module
```

| Dimension | Header Unit | Named Module |
|-----------|-------------|-------------|
| Macro propagation | No (preprocessed, but macros inside headers don't propagate) | No |
| Symbol isolation | Full isolation | Full isolation |
| Header compatibility | Directly wraps existing headers | Requires rewriting interfaces |
| Build cost | Faster than `#include` (BMI cache) | Optimal (precise export) |
| Tool support | MSVC good, Clang/GCC experimental | Primary support across compilers |
| Use case | Migration transition | New projects preferred |

```cpp
// Understanding Header Units equivalently
import <vector>;
// Equivalent to (conceptually):
// 1. Preprocess <vector> (expand all macros)
// 2. Compile preprocessed declarations into BMI
// 3. import statement references that BMI
// Key: macros do not propagate to importers — but macros within the header still work normally
```

## Global Module Fragment: Macros and Legacy Header File Boundary

```cpp
module;                          // ← Global Module Fragment begins

// In this region you can use macros, #include legacy headers
#define USE_LEGACY_API 1
#include <cstdio>
#include <cstdint>
#include "legacy_header.h"      // header files from legacy code

export module modern_api;        // ← module purview begins

// Here you can use symbols introduced in the Global Module Fragment
// But macros and header content are not exposed to importers

export void modern_print(const char* msg) {
    std::printf("[MODERN] %s\n", msg);  // cstdio's printf is available
}

export struct Config {
    uint8_t version;             // cstdint's uint8_t is available
    char name[64];
};
```

**Key rules**:
- `#include` content in the Global Module Fragment belongs to the **global module**, not to the current module
- Macro definitions work normally in the Global Module Fragment but do not propagate to `import` users
- `export` declarations cannot appear in the Global Module Fragment
- The Global Module Fragment must precede `export module`

**Incorrect usage**:

```cpp
export module bad;

#include <string>   // Error! #include in purview → ODR issues
                    // <string>'s declarations are absorbed into the bad module
                    // Other modules importing <string> will have conflicts
```

## Private Module Fragment: Interface and Implementation Separation

```cpp
// widget.cppm — complete module interface + implementation
export module widget;

export class Widget {
public:
    Widget(int id);
    void process();
    int id() const;
private:
    int id_;
};

// Private Module Fragment: declarations after this are not externally visible
module :private;

// The following implementation is not visible to importers
// Changing code here does not require recompiling importers (only relinking)

Widget::Widget(int id) : id_(id) {}

void Widget::process() {
    // Complex implementation details
}

int Widget::id() const { return id_; }
```

**Value of Private Module Fragment**:
- **Interface/implementation in the same file**: suitable for small modules
- **Incremental compilation friendly**: modifying code after `module :private` does not require recompiling dependents
- **Limitation**: Private Module Fragment cannot contain implicit instantiation points for template definitions

## Template Behavior in Modules

### Exporting Template Definitions

```cpp
// math_utils.cppm
export module math_utils;

// Template definitions must be visible to importers
// because importers may need to instantiate
export template <typename T>
T square(T x) {
    return x * x;  // definition must be exported (or visible in interface)
}

// Explicit instantiation export
export template class std::vector<int>;  // export the instantiation of vector<int>

// Implicit instantiation: importers need the full definition for instantiation
// The module's BMI contains template definitions, so importers can directly instantiate
```

### Instantiation Control

```cpp
// widget.cppm (interface)
export module widget;
export template <typename T>
class Container {
    T* data_;
    size_t size_;
public:
    Container(size_t n);
    ~Container();
    // Declared in interface
};

// widget_impl.cpp (implementation unit)
module widget;
// Explicit instantiation definition — compiler generates code here
template class Container<int>;
template class Container<double>;
// Other types require implicit instantiation, potentially causing linker issues
```

## ABI vs BMI: Modules Do Not Provide ABI Stability

```
Relationship between ABI and BMI:

ABI (Application Binary Interface):
  - Object file symbol layout, calling conventions, name mangling
  - Cross-compilation-unit, cross-compiler-version
  - C ABI is stable (extern "C"), C++ ABI is unstable

BMI (Binary Module Interface):
  - Compiler-internal serialized AST
  - Compiler-private format, not cross-version
  - Used only at compile time, does not enter linking

Conclusion: Modules do not improve ABI stability
  - Modifying a module interface → must recompile all importers
  - BMI incompatible → full recompile after changing compiler version
  - Modules' goal is compilation speed, not ABI stability
```

```cpp
// Practical implications
// 1. Library distribution still needs traditional header + precompiled library model
// 2. Modules are suitable for use within a single project
// 3. Cross-project dependencies temporarily still need #include or Header Unit

// Library distributed to external users (Modules not yet supported):
// mylib.h  ← public header
// mylib.lib / libmylib.a  ← precompiled library
// User #includes "mylib.h" + links mylib.lib

// Within a project (strongly recommended):
// math.cppm → import math;  ← same compiler version only
```

## Minimal CMake Project Example

### CMakeLists.txt (CMake 3.28+)

```cmake
cmake_minimum_required(VERSION 3.28)
project(modules_demo LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# Enable module dependency scanning
set(CMAKE_CXX_MODULE_STD 1)           # supports import std (CMake 3.30+)

# Module interface files declared as CXX_MODULE_SOURCES
add_library(math_utils)
target_sources(math_utils
    PUBLIC FILE_SET CXX_MODULES FILES
        src/math_utils.cppm
    PRIVATE
        src/math_utils_impl.cpp       # implementation unit (optional)
)

# Executable
add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE math_utils)
```

### Module Interface File

```cpp
// src/math_utils.cppm
export module math_utils;

export namespace math {
    constexpr int add(int a, int b) { return a + b; }
    constexpr int mul(int a, int b) { return a * b; }

    template <typename T>
    constexpr T clamp(T val, T lo, T hi) {
        return (val < lo) ? lo : (hi < val) ? hi : val;
    }
}
```

### Using the Module

```cpp
// src/main.cpp
import math_utils;
import <iostream>;

int main() {
    std::cout << math::add(1, 2) << '\n';
    std::cout << math::clamp(42, 0, 100) << '\n';
}
```

### Build Commands

```bash
# CMake configure (requires a module-capable compiler)
cmake -B build -G Ninja \
    -DCMAKE_CXX_COMPILER=clang++-18    # Clang 18+
    # or -DCMAKE_CXX_COMPILER=cl       # MSVC
    # or -DCMAKE_CXX_COMPILER=g++-14   # GCC 14+

# Build
cmake --build build
```

## MSVC / GCC / Clang Practical Differences

### Compiler Flags

```
MSVC (cl.exe):
  /std:c++20                    enable C++20
  /interface                    mark as module interface unit (.ixx / .cppm)
  /internalPartition            mark as module internal partition
  /ifcOutput <dir>              BMI output directory
  /reference <name>=<ifc>       manually specify BMI path (not recommended)

Clang (clang++):
  -std=c++20 -fmodules          enable modules
  -fprebuilt-module-path=<dir>  specify BMI search path
  -fmodules-cache-path=<dir>    module cache directory
  --precompile                  only generate BMI (don't compile to .o)
  -fmodule-file=<name>=<pcm>   manually specify single module BMI

GCC (g++):
  -std=c++20 -fmodules-ts       enable modules (experimental)
  -fmodule-mapper=<file>        specify module mapping via file
  -fmodule-header               compile header as Header Unit
  -x c++-system-header <h>      compile system header as Header Unit
```

### File Extension Conventions

```
MSVC:    .ixx (module interface), .cppm (partial support), .cpp (implementation/ordinary)
Clang:   .cppm (module interface), .cpp (implementation/ordinary)
GCC:     .cppm (module interface), .cpp (implementation/ordinary)
Recommended: .cppm (best cross-compiler compatibility)
```

### Compiler Support Matrix (2025)

```
Feature                    MSVC 19.38+  Clang 18+  GCC 14+
───────────────────────────────────────────────────────
export module / import     ✅           ✅         ✅
Module partition           ✅           ✅         ⚠️ partial
Global module fragment     ✅           ✅         ⚠️ experimental
Private module fragment    ✅           ✅         ⚠️ experimental
Header Unit                ✅           ⚠️ partial ⚠️ experimental
import std                 ✅           ⚠️ partial ⚠️ experimental
BMI incremental compile    ✅           ✅         ❌
CMake module support       ✅           ✅         ⚠️ limited
Production ready           ✅           ✅         ❌ not recommended
```

## Module Partition Organization Patterns

### Pattern 1: Layer-based Partitions

```cpp
// network:socket.cppm — low-level networking
export module network:socket;
export class Socket { /* ... */ };

// network:http.cppm — HTTP layer (depends on socket)
export module network:http;
import :socket;
export class HttpClient { /* ... */ };

// network.cppm — main interface (aggregate + re-export)
export module network;
export import :socket;
export import :http;
```

### Pattern 2: Functional Domain Partitions

```cpp
// app:ui.cppm
export module app:ui;
export void render_dashboard();

// app:backend.cppm
export module app:backend;
export void start_server(int port);

// app:config.cppm
export module app:config;
export struct AppConfig { int port; bool debug; };

// app.cppm
export module app;
export import :config;
export import :ui;
export import :backend;
```

### Pattern 3: Internal Partitions (Not Exported)

```cpp
// engine:detail_math.cppm — internal math utilities
export module engine:detail_math;
// This partition can be imported by other partitions of engine
// But cannot be directly imported externally (unless the main module does export import)

// engine:render.cppm
export module engine:render;
import :detail_math;  // internal use

// engine.cppm
export module engine;
export import :render;
// Note: no export import :detail_math → not externally visible
```

**Partition naming conventions**:
- Before `:` is the module name, after is the partition name
- Prefix internal implementation partitions with `detail_`
- Main module selectively uses `export import` — controls the public API surface

## Migration Strategy from Headers to Modules

### Gradual Migration Roadmap

```
Phase 0: Assessment (1-2 weeks)
  ├── Audit header dependency graph
  ├── Identify leaf nodes (utility libraries with no internal dependencies)
  └── Confirm compiler version support

Phase 1: Leaf node conversion (2-4 weeks)
  ├── Convert utility libraries (string_utils, math_utils) to modules
  ├── Keep compatibility headers alongside original #include
  ├── Verify compilation correctness and speed
  └── Gradually migrate consumers to modules

Phase 2: Bridging layer (4-8 weeks)
  ├── Convert core libraries to modules
  ├── Create Header Units for unmigrated headers
  ├── Import converted modules within modules
  └── Keep #include compatibility during transition

Phase 3: Full migration (ongoing)
  ├── Replace #include with import layer by layer
  ├── Remove compatibility headers
  ├── Optimize module boundaries (reduce unnecessary exports)
  └── Continuously monitor compilation speed and correctness
```

### Migration Code Example

```cpp
// Phase 0-1: maintain both interfaces
// utils.h (compatibility header)
#pragma once
import utils_module;    // header internally imports module

// New code directly imports
// import utils_module;

// Phase 2: bridge legacy code in a module
module;
#include <legacy_header.h>  // legacy code still in Global Module Fragment
export module new_module;

export using legacy::OldClass;  // selectively export legacy symbols
export void modern_api();
```

### Migration Notes

```
1. Macro issues
   ├── Macros cannot cross module boundaries → use constexpr / inline functions instead
   ├── Assert macros (assert) work normally in Global Module Fragment
   └── Configuration macros replaced with constexpr variables

2. Header order dependencies
   ├── Modules eliminate order dependency (each module compiled independently)
   ├── But in legacy code, if A.h depends on B.h being included first
   └── Still needs attention in Global Module Fragment

3. Template explicit instantiation
   ├── Explicit instantiation in modules behaves differently from headers
   ├── Instantiation in implementation units is not automatically exported
   └── Needs explicit declaration in interface: export template class ...

4. ODR (One Definition Rule)
   ├── Module boundaries automatically provide ODR protection
   ├── Same entity defined in different modules → compile error
   └── Anonymous namespace behavior in modules requires special attention

5. Build system changes
   ├── CMake 3.28+ has native support
   ├── Ninja 1.11+ supports module dependency graphs
   ├── Older build systems (Makefile, Bazel) need additional adaptation
   └── CI/CD environments must lock compiler version
```

## Summary

```
Modules Full Build Chain
─────────────────────────────────────────────────
Source:     .cppm (interface) / .cpp (implementation)
    ↓
Scanner:    P1689 dependency graph → JSON
    ↓
Scheduler:  topological sort → compilation order
    ↓
Compiler:   interface → BMI (.ifc/.pcm/.gcm)
            implementation → .o
            consumer → import BMI → .o
    ↓
Linker:     .o → final binary
─────────────────────────────────────────────────

Key constraints:
  BMI format is compiler-private, not cross-version
  All developers use same compiler + version
  CMake 3.28+ / Ninja 1.11+ is minimum requirement
  Large projects should migrate gradually, leaf nodes first
```
